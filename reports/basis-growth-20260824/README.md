# Mining basis words under #41's MDL criterion

Date: 2026-08-24 · corpus `deep-corpus-v1` · basis `wl-core-v1`

## Result

**#41's acceptance criterion is degenerate.** Run as written it does not
converge, and the compression it buys is paid for with search cost several
orders of magnitude larger.

| | before | after |
|---|---:|---:|
| basis size | 118 | **518** |
| corpus ops | 137,140 | 87,190 |
| effective branching `b_eff` | 17.84 | **105.42** |
| search cost at depth 6 | 1x | **42,631x** |

400 words accepted, cutting the corpus 36.4%. The run **hit its 400-round cap
rather than converging** — the criterion had not stopped accepting.

Reproduce:

```
uv run python experiments/mine_basis_words.py --report-dir reports/basis-growth-20260824
```

## Why it does not converge

The criterion accepts a word iff naming it eliminates more than
`(log2(B+1) - log2(B)) / log2(B+1)` of total corpus ops. That bar **falls as
the basis grows**: 0.177% at `B = 118`, and roughly 0.031% at `B = 518`. Each
acceptance makes the next one cheaper to justify, so there is no fixed point —
only a slowly retreating one.

## Why the trade is bad

Description length and search difficulty are different quantities, and the
criterion contains only the first. Adding an applicable word raises `b_eff` by
about 1, and search cost goes as `b_eff**d`.

The three-word run makes it legible: **three accepted words cost 1.49x search
at depth 6 for 2.7% compression.** Four hundred words cost 42,631x for 36.4%.
Compression is linear in words accepted; search cost is exponential.

## Candidates to reject by hand

**68 of the 400 accepted are flagged.** MDL accepts all of them.

- **Digest projection.** The top candidate overall, `int_to_str str_hash`, and
  27 others. `str_hash` is SHA-256, so these compose to "hash this value and
  read bits off the digest". Deterministic, genuinely frequent, and a lookup
  table rather than compositional structure. Naming it would bake an accidental
  constant source into the basis.
- **One-op repeats.** `square square`, `double double` and others. These say
  nothing the length-one op does not; they are frequent because the corpus was
  generated by expansion, which applies the same op twice as readily as twice
  different ones.

Both classes were predicted before the run and both appear at the top. A
frequency-driven criterion cannot distinguish them from real abstractions,
which is an argument for a human read of any candidate list — or for a second
criterion that prices what the word *does* rather than how often it appears.

## What to do with the criterion

It needs a second term. Reporting both numbers per candidate — the MDL delta
and the `b_eff` delta — is what these tables do, and it makes the trade
visible instead of optimising one objective blind. Setting the exchange rate
between them is a decision this issue should make explicitly, and the natural
form is a budget: accept while `b_eff**d` stays under whatever certified
depth the corpus pipeline needs.
